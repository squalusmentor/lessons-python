# Урок L5. ООП: от классов до паттернов

В прошлых уроках данные и поведение жили порознь: словарь отдельно, функции
отдельно. В L4 мы даже видели, как один словарь и печатают (`build_message(**d)`),
и материализуют в объект (`WeatherData(**d)`). **ООП** связывает данные с их
поведением и инвариантами в одном месте — в **классе**.

Урок разбит на **два занятия**:

- **Занятие 1** — фундамент: инкапсуляция, наследование, полиморфизм,
  dunder-методы. После него делаем **часть 1 практики** — классы предметов.
- **Занятие 2** — `property`, **композиция против наследования**, паттерны
  (фабрика, синглтон). После него — **часть 2 практики**: геокаталог IP-адресов.

Главная мысль урока: **ООП ради задачи, а не ради синтаксиса**. Класс оправдан,
когда у данных есть инвариант, который надо держать, или когда разные сущности
обязаны отвечать на один и тот же вызов.

# Занятие 1. Инкапсуляция, наследование, полиморфизм, dunder

## 1. Классы и инкапсуляция

Файл: [01_classes_encapsulation.py](01_classes_encapsulation.py)

**Класс** — это «чертёж» объекта: он описывает, какие у объекта данные
(**атрибуты**) и что он умеет (**методы**). **Объект** (экземпляр) создаётся
вызовом класса как функции:

```python
class Product:
    def __init__(self, name, quantity):
        self.name = name          # атрибут экземпляра
        self._quantity = quantity

p = Product("Молоток", 5)         # создали объект
```

- `__init__` — **конструктор**, вызывается при создании объекта. Это не «создание»
  в чистом виде (за него отвечает `__new__`), а **инициализация** уже созданного.
- `self` — ссылка на сам объект. В Python он передаётся **явно** первым параметром
  каждого метода. В отличие от `this` в Java/C++, тут он виден в сигнатуре.

### Атрибут класса против атрибута экземпляра

```python
class Product:
    category = "товар"            # атрибут КЛАССА — один на всех
    def __init__(self, name):
        self.name = name          # атрибут ЭКЗЕМПЛЯРА — свой у каждого
```

Атрибут класса хранится в одном месте и виден всем экземплярам. Если присвоить
`p.category = "..."`, создастся **атрибут экземпляра**, который «затенит» классовый
только для этого объекта. **Ловушка**: изменяемый атрибут класса (`items = []`)
будет общим для всех — это аналог ловушки изменяемого аргумента по умолчанию из
L4. Списки/словари как состояние объекта заводи в `__init__`, а не на уровне класса.

### Инкапсуляция

Инкапсуляция — это про то, чтобы **спрятать внутреннее устройство** и пускать к
данным только через методы, которые держат **инварианты**. В нашем складе
инвариант — «количество не уходит в минус». Поэтому количество меняем не напрямую,
а через `restock()` / `take()`, и они проверяют корректность.

**В Python нет настоящих private-полей.** Есть две договорённости:

- `_one_underscore` — «внутреннее, снаружи не трогай». Чисто сигнал, язык ничего
  не запрещает.
- `__two_underscore` — включает **name mangling**: имя `__x` внутри класса `C`
  превращается в `_C__x`. Это не защита, а защита от **случайного** конфликта имён
  при наследовании. Достать всё равно можно: `obj._C__x`.

То есть приватность в Python — **по соглашению**, а не по принуждению («мы все тут
взрослые люди»). Это отличается от `private` в Java/C++, где компилятор запрещает
доступ.

## 2. Наследование

Файл: [02_inheritance.py](02_inheritance.py)

Наследование выражает связь **«является»** (IS-A): `Book` **является** `Item`.
Подкласс получает все атрибуты и методы родителя и может их дополнять или
переопределять.

```python
class Item:
    def __init__(self, name, quantity):
        self.name = name
        self.quantity = quantity
    def label(self):
        return f"{self.name} ({self.quantity} шт.)"

class Book(Item):                       # Book наследует Item
    def __init__(self, name, quantity, author):
        super().__init__(name, quantity)  # вызвали конструктор родителя
        self.author = author
    def label(self):                    # переопределение (override)
        return super().label() + f", автор: {self.author}"
```

- `super()` обращается к родителю. Через него зовут родительский `__init__`, чтобы
  **не дублировать** его код, и дополняют переопределённый метод вместо полной
  перезаписи.
- `isinstance(obj, Class)` — проверка «объект этого класса или его наследника».
- `issubclass(Sub, Base)` — проверка «класс — наследник другого».

### Множественное наследование и MRO (коротко)

Python **разрешает** наследоваться от нескольких классов. Порядок поиска методов
определяется **MRO** (Method Resolution Order, алгоритм C3); посмотреть его можно
через `Class.__mro__`. Это мощно, но быстро запутывает, поэтому на практике
обычно держатся **одиночного** наследования, а для «подмешивания» поведения
используют узкие **mixin**-классы. Глубоко в MRO здесь не лезем.

**Главная мысль:** наследование — это не «способ переиспользовать код любой ценой».
Это утверждение «подкласс — частный случай родителя». Если это не так — нужна
**композиция** (занятие 2).

## 3. Полиморфизм и утиная типизация

Файл: [03_polymorphism.py](03_polymorphism.py)

**Полиморфизм** — один и тот же вызов (`obj.label()`) работает по-разному в
зависимости от типа объекта. Код, который перебирает объекты, **не знает и не
должен знать** их конкретный класс:

```python
for it in items:           # items — это и Book, и Tool, и Item
    print(it.label())      # у каждого вызовется СВОЙ label()
```

### Утиная типизация (duck typing)

В Python для полиморфизма **не обязателен общий родитель**. Важно лишь, чтобы у
объекта был нужный метод:

> «Если оно выглядит как утка и крякает как утка — это утка.»

```python
def chorus(animals):
    for a in animals:
        print(a.voice())   # неважно, какой класс — лишь бы умел voice()
```

Это отличается от статически типизированных Go/Java, где обычно нужен общий
интерфейс или базовый тип. В Python проверка происходит **в момент вызова**: есть
метод — работает, нет — `AttributeError`.

### Абстрактные базовые классы (abc)

Когда хочется **зафиксировать контракт** («все фигуры обязаны уметь `area()`»),
берут модуль `abc`:

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...
```

Класс с нереализованным `@abstractmethod` **нельзя создать** — `Shape()` бросит
`TypeError`. Это заставляет наследников реализовать метод и документирует
ожидаемый интерфейс. Часто это удобнее, чем «голая» утиная типизация.

## 4. Dunder-методы

Файл: [04_dunder.py](04_dunder.py)

**Dunder** (double underscore, `__like_this__`), они же «магические» методы, —
это крючки, через которые объект подключается к синтаксису и встроенным функциям
языка. Ты их **определяешь**, а Python **вызывает** в нужный момент.

| Пишешь        | Python зовёт      | Зачем                              |
|---------------|-------------------|------------------------------------|
| `repr(x)`     | `__repr__`        | строка для отладки/REPL            |
| `print(x)`    | `__str__`         | строка для человека                |
| `x == y`      | `__eq__`          | равенство                          |
| `x < y`       | `__lt__`          | сравнение -> `sorted`, `min`/`max` |
| `x + y`       | `__add__`         | перегрузка оператора               |
| `len(x)`      | `__len__`         | длина                              |
| `i in x`      | `__contains__`    | проверка вхождения                 |
| `x[i]`        | `__getitem__`     | индексация (и итерация как бонус)  |
| `hash(x)`     | `__hash__`        | использование в `set`/ключах `dict`|

Ключевые тонкости:

- **`__repr__` против `__str__`.** `__repr__` — для разработчика, желательно
  однозначный (в идеале — валидный код, воссоздающий объект). `__str__` — для
  человека. Нет `__str__` — `print` использует `__repr__`. Минимум — всегда
  определяй `__repr__`, иначе в логах будет `<object at 0x...>`.
- **`__eq__` и `__hash__` ходят парой.** Если определил `__eq__`, объект по
  умолчанию становится **нехешируемым** (его нельзя класть в `set`/ключи `dict`).
  Чтобы вернуть хешируемость, определи `__hash__` — и считай хеш по **тем же**
  полям, что и равенство.
- **Сравнения.** Хватает `__lt__`, чтобы заработали `sorted`, `min`, `max`. Если
  нужны все операторы (`<`, `<=`, `>`, `>=`), допиши их или повесь декоратор
  `functools.total_ordering`.
- Возвращай `NotImplemented` (а не `False`!) из `__eq__`/`__lt__`, когда тип
  «другого» операнда неподходящий — это даёт Python шанс попробовать обратную
  операцию.

# Занятие 2. property, композиция против наследования, паттерны

## 5. property — умные атрибуты

Файл: [05_property.py](05_property.py)

В занятии 1 мы прятали количество за методами `restock`/`take`. Но иногда хочется,
чтобы снаружи всё выглядело как **обычный атрибут** (`obj.x`), а под капотом
работала логика. Для этого есть `property`.

```python
class Item:
    def __init__(self, quantity):
        self.quantity = quantity      # сразу идёт через сеттер -> валидация в __init__

    @property
    def quantity(self):               # геттер: вызывается на чтение obj.quantity
        return self._quantity

    @quantity.setter
    def quantity(self, value):        # сеттер: вызывается на запись obj.quantity = ...
        if value < 0:
            raise ValueError("количество не может быть отрицательным")
        self._quantity = value
```

Снаружи это по-прежнему `it.quantity` и `it.quantity = 5` — **внешний код не
меняется**, а валидация уже на месте.

**Почему не `get_quantity()`/`set_quantity()` как в Java?** В Python так **не
принято**. Идиома: начинаешь с обычного публичного атрибута, а когда позже
понадобится валидация или вычисление — превращаешь его в `property`. Интерфейс
остаётся прежним, ничей код не ломается. Поэтому геттеры/сеттеры «на всякий
случай» в Python — это лишний код.

Что ещё умеет `property`:

- **Вычисляемое свойство только для чтения** — определи только геттер (без
  сеттера). Попытка присвоить -> `AttributeError`. Пример: `fahrenheit`, которое
  считается из `celsius` и нигде не хранится.
- **`@x.deleter`** — крючок на `del obj.x` (нужен редко).

## 6. Композиция против наследования

Файл: [06_composition_vs_inheritance.py](06_composition_vs_inheritance.py)

Два способа собрать сложное из простого:

- **Наследование** — «X **является** Y» (IS-A). `Book` является `Item`.
- **Композиция** — «X **содержит** Y» (HAS-A). `Car` содержит `Engine`.
  `Inventory` содержит предметы.

Правило большого пальца: **предпочитай композицию**. Наследуйся, только когда
подкласс действительно **является** родителем и обязан быть с ним
**взаимозаменяем** (принцип подстановки Барбары Лисков).

### Классический антипример: `Stack(list)`

Соблазнительно сделать стек, унаследовав `list` — ведь там уже есть `append` и
`pop`. Но так стек **протекает**: вместе с нужным он получает `insert`, `sort`,
`reverse`, `[i] = ...` — и кто угодно может нарушить дисциплину «только сверху».
Инкапсуляция сломана **самим наследованием**.

```python
class Stack:                  # ПРАВИЛЬНО: композиция + делегирование
    def __init__(self):
        self._items = []      # список ВНУТРИ, наружу не торчит
    def push(self, x):
        self._items.append(x) # делегируем работу внутреннему списку
    def pop(self):
        return self._items.pop()
```

Теперь наружу торчит **ровно** нужный интерфейс (`push`/`pop`), а как он устроен
внутри — наше дело. Передача вызова внутреннему объекту называется
**делегированием**.

Почему композиция чаще лучше:

- **меньше связанность** — ты зависишь от узкого интерфейса части, а не от всего
  огромного API родителя;
- **гибкость** — внутреннюю реализацию можно заменить, не трогая наследников;
- **нет хрупкого базового класса** — изменение родителя не ломает неожиданно всех
  потомков.

Наследование оставляем для настоящих IS-A: `Book`/`Tool` против `Item` — это
честное наследование (книга **является** предметом инвентаря).

## 7. Паттерны: фабрика, синглтон, методы класса

Файл: [07_patterns.py](07_patterns.py)

**Паттерн проектирования** — типовое, проверенное решение часто встречающейся
задачи. Разберём два самых ходовых плюс декораторы методов.

### @classmethod и @staticmethod

Это всё те же **декораторы** (из L4), но навешенные на методы:

- **`@classmethod`** получает первым аргументом сам **класс** (`cls`), а не
  экземпляр. Главное применение — **альтернативный конструктор** (фабрика):

  ```python
  class Item:
      @classmethod
      def from_dict(cls, data):
          return cls(data["name"], data["quantity"])
  ```

  Это прямое продолжение темы L4 «словарь -> объект»: команда CLI или строка JSON
  превращается в готовый объект. `cls` (а не жёстко `Item`) важен: в подклассе
  фабрика создаст объект **подкласса**.
- **`@staticmethod`** не получает ни `self`, ни `cls` — это просто функция, живущая
  в неймспейсе класса (например, валидатор `is_valid_name`). Берут, когда логика
  по смыслу относится к классу, но не нуждается в его данных.

### Фабрика

**Фабрика** прячет выбор конкретного класса за одной точкой создания. В проекте
`Item.from_dict({"type": "tool", ...})` сама решит, создать `Book`, `Tool` или
базовый `Item`. Плюс: код, добавляющий предметы, не пишет длинных `if/elif` по
типу — он просто отдаёт словарь.

### Синглтон

**Синглтон** гарантирует, что объект класса существует **в единственном
экземпляре**, и даёт к нему общую точку доступа. В проекте таким будет
`Warehouse` — единый склад на всё приложение.

Три способа в Python (от простого к «хитрому»):

```python
# 1. Самый питоничный — просто модуль-уровень. Модуль грузится один раз,
#    значит и объект в нём один.
warehouse = Warehouse()        # импортируй и пользуйся везде одним и тем же

# 2. Через __new__ — класс сам возвращает один и тот же объект.
class Config:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# 3. Через декоратор-замыкание (см. L4).
```

**Осторожно с синглтоном.** Это по сути **глобальное состояние** в обёртке.
Плюс — один общий ресурс (конфиг, пул соединений, логгер). Минусы — скрытая
зависимость (функция тихо лезет к глобальному объекту) и боль с тестами (состояние
течёт между тестами). Часто чище **создать объект один раз и явно передать** его
туда, где он нужен (dependency injection). Синглтон — инструмент, а не самоцель.

### Где ещё ООП «ради задачи»

Темы переплетаются: фабрика опирается на `@classmethod`, синглтон-декоратор — на
замыкания из L4, а **таблица диспетчеризации** (словарь «строка -> функция/класс»
из L4) — это лёгкая альтернатива и фабрике, и паттерну «Стратегия». Паттерн бери
тогда, когда он **снимает реальную боль**, а не «чтобы было по канону».

`property` и dunder-методы ведут прямо к **`@dataclass`** — он генерирует
`__init__`, `__repr__`, `__eq__` за тебя, оставляя место и для валидации. А
паттерны, абстрактные классы и композиция — это словарь, на котором написана
архитектура реальных приложений. Это темы следующих блоков.
