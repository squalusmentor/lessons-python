# Часть 1. Зачем это всё: конкурентность против параллелизма

Два слова, которые постоянно путают.

- **Параллелизм (parallelism)** — задачи реально выполняются *одновременно*, на
  разных ядрах CPU. Два ядра — два потока байткода в одну и ту же микросекунду.
- **Конкурентность (concurrency)** — задачи *продвигаются вперемешку* на одном
  исполнителе: чуть одну, чуть другую, переключаясь между ними. В любой момент
  времени работает ровно одна, но за секунду продвинулись все.

asyncio даёт **конкурентность без параллелизма**: один поток, одно ядро, но
пока одна корутина ждёт ответ из сети, поток занимается другими. Это выигрывает
там, где программа **не считает, а ждёт**.

### I/O-bound против CPU-bound — от этого зависит выбор инструмента

| Тип нагрузки | Чем занят процесс | Пример | Что помогает |
|---|---|---|---|
| **I/O-bound** | **ждёт** внешний ресурс (сеть, диск, БД) | 100 HTTP-запросов, поход в Postgres | **asyncio** или потоки |
| **CPU-bound** | **считает** (грузит ядро) | хеши, обработка картинок, перемножение матриц | **процессы** (multiprocessing) |

Ключевое наблюдение: когда ты делаешь HTTP-запрос, твой CPU почти всё время
**простаивает** — данные ползут по сети, а процессор ждёт. Отправить запрос
занимает микросекунды, ответ идёт сотни миллисекунд. Всё это время можно было
бы отправить ещё 99 запросов. Именно этот простой asyncio и утилизирует.

А вот перемножение матриц процессор грузит на 100% — «переключаться» там не на
что, ждать нечего. asyncio такой задаче не поможет вообще (об этом — часть 8).

**asyncio — это про I/O-bound.** Держать тысячу медленных сетевых соединений на
одном потоке — его коронный номер.

# Часть 2. GIL по-настоящему

**GIL (Global Interpreter Lock)** — глобальный замок интерпретатора CPython:
в любой момент байткод Python исполняет **ровно один поток**, даже на 16 ядрах.
Потоки в Python есть и переключаются, но по-настоящему параллельно **считать**
они не могут — замок один, и держит его кто-то один.

Почему так сделано: управление памятью в CPython (подсчёт ссылок) не
потокобезопасно, и GIL — самый дешёвый способ это обойти. Плата — отсутствие
параллелизма для чистого Python-кода.

**Важнейший нюанс: GIL отпускается на время блокирующих syscall'ов.** Когда C-код
уходит ждать I/O (`recv()` из сокета, чтение файла), он говорит «я встал в
ожидание, замок не держу» — и другой поток может в это время исполнять байткод.
Поэтому:

- для **I/O-bound** потоки полезны: пока один ждёт сеть с отпущенным GIL, другой
  работает;
- для **CPU-bound** потоки почти бесполезны: оба хотят *считать*, а замок один —
  они выстраиваются в очередь и толку от второго ядра ноль.

(С Python 3.13 появилась экспериментальная free-threaded сборка без GIL, но это
пока не мейнстрим — рассчитывай на GIL.)

**И сразу главное про asyncio: GIL к нему почти не относится.** У event loop
всего **один поток**. Ему не с кем делить замок — конкуренции за GIL просто нет.
Проблема asyncio совсем другая: не «замок занят», а «нет точки, где можно
переключиться». Об этом — дальше.

# Часть 3. Event loop по-настоящему

**Event loop** — это цикл в одном потоке, который крутит очередь готовых к
выполнению корутин. Огрублённо он делает вот что, по кругу:

```
пока есть работа:
    1. выполни все корутины, готовые прямо сейчас, — каждую до ближайшего await
    2. спроси у ОС (через epoll/kqueue/select): какие сокеты/таймеры уже готовы?
       — на этом шаге поток СПИТ, если готовых нет и все ждут I/O
    3. корутины, чьё ожидание завершилось, верни в очередь готовых
    4. повтори
```

Шаг 2 — сердце всего. Loop не опрашивает сокеты в цикле (это жгло бы CPU). Он
отдаёт список интересующих его дескрипторов операционной системе через механизм
**мультиплексирования I/O** (`epoll` на Linux, `kqueue` на macOS, IOCP/`select`
на Windows) и **засыпает**, пока ОС не разбудит его словами «вот эти сокеты
готовы к чтению». Ноль потраченного CPU на ожидание.

### Кооперативная многозадачность против вытесняющей

Вот принципиальная разница между asyncio и потоками:

- **Потоки — вытесняющая (preemptive) многозадачность.** ОС может отобрать
  управление у потока **в любой момент**, между любыми двумя инструкциями. Ты не
  контролируешь, где произойдёт переключение, — отсюда гонки данных, блокировки,
  мьютексы.
- **asyncio — кооперативная (cooperative) многозадачность.** Корутина работает,
  пока сама не дойдёт до `await` и **добровольно не отдаст** управление. Между
  двумя `await` код исполняется атомарно — никто не влезет. Переключения
  происходят **только в точках `await`**, явно и предсказуемо.

Отсюда два следствия. Хорошее: в async-коде почти не нужны блокировки — ты
точно знаешь, где тебя могут прервать. Плохое (и это ловушка №1 новичка): если
между `await`'ами ты **надолго завис** (блокирующий вызов или тяжёлый расчёт),
ты **не отдал** управление — и весь loop, все остальные корутины, стоят колом.
Кооперативность работает, только пока все «сотрудничают».

### Корутина — это машина состояний, а `await` — точка сохранения

Что вообще значит «корутина приостановилась и отдала управление»? Под капотом
корутина — родственник генератора: функция, которая умеет **замереть на строке,
сохранив все свои локальные переменные, и позже продолжить ровно оттуда**.

- `async def` создаёт функцию, возвращающую **объект-корутину** (не результат!);
- `await X` означает «начни ждать X; если X ещё не готов — **заморозь меня** и
  верни управление тому, кто меня крутит (event loop)»;
- когда X готов, loop делает корутине `.send(результат)`, и она **оживает** с той
  же строки, с теми же локальными переменными.

Именно поэтому «переключение контекста» в asyncio почти бесплатное: это не
переключение потоков силами ОС (дорого, тысячи тактов), а обычный возврат из
функции и последующий вызов `.send()` — всё в пользовательском коде.

`Task` — это корутина, которую loop взял «в работу» (запланировал в очередь).
`Future` — объект-обещание «здесь однажды появится результат»; на нём удобно
`await`'ить. `asyncio.create_task(coro)` оборачивает корутину в Task и ставит в
очередь; сама корутина без этого никуда не поедет.

Практику по всему этому — в `01_coroutines.py` и `02_event_loop.py`.

# Часть 4. Синтаксис: `01_coroutines.py`, `02_event_loop.py`

## Корутина не запускается сама

Файл: [01_coroutines.py](01_coroutines.py)

```python
async def greet(name):
    await asyncio.sleep(1)
    return f"привет, {name}"

coro = greet("мир")        # тело greet ещё НЕ выполнялось! coro — объект-корутина
result = asyncio.run(coro) # вот теперь loop прокрутил корутину и вернул результат
```

Три способа «запустить» корутину:

- `asyncio.run(coro)` — **точка входа** из синхронного мира. Поднимает event
  loop, крутит корутину до конца, гасит loop. Вызывается **один раз** на
  программу, обычно в `main`.
- `await coro` — **внутри** другой корутины: дождаться результата.
- `asyncio.create_task(coro)` — запланировать в фоне, не дожидаясь здесь же.

Забыл `await` / `run` — корутина не выполнится, а Python буркнет
`RuntimeWarning: coroutine '...' was never awaited`. Это первый симптом «где-то
потерял await».

## `await` по очереди — это последовательно

Файл: [02_event_loop.py](02_event_loop.py)

Частое заблуждение: «поставил `async` — стало быстро». Нет. Вот это —
**последовательно**, ~2 секунды:

```python
a = await greet("Аня", 1.0)     # ждём 1 с здесь
b = await greet("Боря", 1.0)    # и только потом ещё 1 с
```

`await` означает «дождись прямо здесь». Чтобы корутины пошли **конкурентно**,
их надо сначала все запланировать, а уже потом ждать — это делает `gather`:

```python
a, b = await asyncio.gather(greet("Аня", 1.0), greet("Боря", 1.0))   # ~1 с
```

`gather` запускает всё разом и ждёт, пока завершатся все. Их ожидания
**накладываются** — общее время равно самому долгому, а не сумме. Именно на этом
построен весь выигрыш async в сети (часть 6).

# Часть 5. Синхронный запрос против асинхронного — под капотом

Это — сердцевина урока. Разберём **буквально по syscall'ам**, что происходит,
когда ты запрашиваешь страницу, и почему `requests` вешает поток, а `aiohttp` —
нет.

## Синхронный `requests.get(url)`: что происходит

1. Python-код зовёт функцию клиента, та открывает TCP-соединение.
2. Драйвер делает syscall `send()` — отправляет HTTP-запрос в сокет.
3. Драйвер делает `recv()` — и **тут блокируется**. ОС переводит поток в
   состояние «ожидание I/O»: поток не ест CPU, но и **не возвращает управление**
   вызывающему коду. Он физически стоит внутри C-функции.
4. Только когда сервер ответит, `recv()` возвращается, и Python-код продолжается.

Ключевое: шаги 2–3 — это **блокирующий syscall**. Если такой вызов случится
внутри `async def`, то с точки зрения event loop'а (он живёт в **том же** потоке)
весь этот промежуток — чёрная дыра. Loop не может туда заглянуть, не может
ничего переключить: поток занят ожиданием внутри C-функции, а не исполняет
Python-байткод, который loop мог бы прервать в точке `await`.

Заметь тонкость: **GIL тут даже не главный затык.** Клиент мог бы отпустить GIL
на время `recv()` (и `requests` это делает — чтобы не блокировать *другие*
потоки). Но asyncio это не спасает: у тебя **один** поток в event loop, и дело
не в замке, а в том, что **нет точки `await`/`yield`**, где loop мог бы
переключиться на другую корутину. Поток ушёл ждать в C — и loop ушёл вместе с ним.

## Асинхронный `await session.get(url)` (aiohttp): что происходит

1. `await session.get(url)` вызывается.
2. Внутри aiohttp сокет переведён в **неблокирующий** режим
   (`socket.setblocking(False)`).
3. Драйвер пытается `send()` — если буфер сокета не готов принять данные, вместо
   блокировки происходит `await` на специальный Future, зарегистрированный в
   event loop через `add_writer`/`add_reader` (а это тот же `selectors`/`epoll`,
   на котором построен сам loop).
4. Корутина **замораживается** в этой точке, управление возвращается в event loop.
5. Loop идёт обслуживать другие готовые корутины (вот тут и печатаются тики из
   демо `05`).
6. Когда ОС через `epoll` сигналит «сокет готов на чтение» — event loop
   **возобновляет именно эту корутину** ровно с того места, где она замерла.

Грубо: aiohttp реализует HTTP поверх **неблокирующих сокетов, интегрированных с
тем же `epoll`**, на котором крутится весь твой loop. Поэтому ожидание ответа —
это не блокировка потока, а «я зарегистрировал интерес к этому сокету, разбудите,
когда будет готово». Один поток тем временем свободен для сотен других соединений.

Вот эта разница и есть весь урок в одной картинке:

```
requests.get():   [--- отправил ---][=== поток СТОИТ, ждёт ответ ===][прочитал]
                                     ^ event loop мёртв всё это время

aiohttp .get():   [--- отправил ---][await: loop крутит ДРУГИЕ корутины][прочитал]
                                     ^ сокет ждёт в epoll, поток занят делом
```

Демо `04` меряет это в секундах, демо `05` показывает вживую.

## То же самое для базы данных (psycopg2 против asyncpg)

С БД история **дословно та же** — её полезно знать, потому что в боевом бэкенде
(тот самый проект, что мы собирали) в сеть ходят не только HTTP-клиенты, но и
драйвер Postgres.

**Синхронный драйвер `psycopg2`.** `cursor.execute("SELECT ...")` под капотом
делает `send()` запроса в сокет Postgres и `recv()` ответа — и на `recv()`
**блокируется** ровно как `requests`. Внутри `async def` это снова вешает весь
loop: нет точки `await`, где можно переключиться. И снова — GIL не главный затык:
драйвер мог бы отпустить замок на время `recv()`, но одному потоку event loop'а
от этого не легче.

**Асинхронный драйвер `asyncpg`.** `await conn.fetch("SELECT ...")` работает
поверх **неблокирующего** сокета: не может отправить/прочитать прямо сейчас —
регистрирует Future в loop через `add_reader`/`add_writer` (тот же `epoll`),
замораживает корутину и возвращает управление. Когда ОС говорит «сокет готов» —
loop будит эту корутину с места остановки. `asyncpg` фактически сам реализует
бинарный wire-протокол Postgres на Cython поверх неблокирующих сокетов, вшитых в
тот же `epoll`, что крутит весь loop. Ожидание ответа БД — не блокировка потока,
а «зарегистрировал интерес, проснусь по готовности».

> Отсюда правило боевого async-бэкенда: **`asyncpg` (или SQLAlchemy async), а не
> `psycopg2`**; **`aiohttp`/`httpx.AsyncClient`, а не `requests`**. Один
> синхронный вызов на горячем пути — и все твои `async def` эндпоинты начинают
> тормозить друг друга, потому что делят один event loop.

# Часть 6. aiohttp на практике

Файлы: [04_sync_vs_async_requests.py](04_sync_vs_async_requests.py),
[05_parallel_request_and_ticks.py](05_parallel_request_and_ticks.py)

## ClientSession — одна на всё приложение

```python
import aiohttp

async def main():
    timeout = aiohttp.ClientTimeout(total=15)
    async with aiohttp.ClientSession(timeout=timeout) as session:
        async with session.get("https://example.com") as response:
            print(response.status)          # int, доступен сразу
            text = await response.text()     # а тело — await: его ещё надо дочитать
```

Три вещи, которые надо усвоить сразу:

- **`ClientSession` создаётся один раз** и переиспользуется для всех запросов.
  Она держит пул TCP-соединений и умеет keep-alive. Поднимать новую сессию на
  каждый запрос — классический антипаттерн (теряешь пул, течёшь ресурсами).
  Отсюда `async with` — сессия закроется корректно.
- **Два `async with`.** Внешний — сессия, внутренний — конкретный запрос-ответ
  (`response` надо закрыть, отсюда контекстный менеджер).
- **Тело ответа — это `await`.** `response.status` есть сразу (заголовки уже
  пришли), а вот `await response.text()` / `.json()` / `.read()` — это ещё одно
  ожидание: тело страницы может идти отдельными пакетами. Каждый такой `await` —
  ещё одна точка, где loop может заняться другими корутинами.

## Сравнение `requests` и `aiohttp` — построчно

| | `requests` (sync) | `aiohttp` (async) |
|---|---|---|
| Запрос | `requests.get(url)` | `async with session.get(url) as r` |
| Тело | `r.text` (сразу) | `await r.text()` (await) |
| JSON | `r.json()` | `await r.json()` |
| Статус | `r.status_code` | `r.status` |
| N запросов | цикл — последовательно | `asyncio.gather(...)` — конкурентно |
| Блокирует поток? | **да** | **нет** |

## Демо `04`: цифры не врут

Качаем 4 URL с задержками 1+2+1+2 секунды:

- `requests` в цикле — **~6 с** (задержки складываются, ждём по одному);
- `aiohttp` через `gather` — **~2 с** (все запросы летят разом, общее время =
  самому долгому ответу).

Разница не в «скорости библиотеки» — байты по проводу идут одинаково. Разница в
том, что async **не простаивает** в ожидании: пока один сокет ждёт, отправлены и
ждут остальные.

## Демо `05`: контекст-свитч вживую (то, ради чего урок)

`blinker()` печатает `tick` каждые 0.3 с. `download()` качает медленную страницу
(сервер отвечает через ~3 с). Запускаем **конкурентно**. Вывод:

```
[0.00с] download: запрос отправлен, впереди await ответа сервера
[0.00с] tick 1   <- loop свободен, пока сокет ждёт ответ
[0.30с] tick 2
[0.60с] tick 3
 ... тики идут, потому что download отдал управление на await ...
[2.70с] tick 10
[3.10с] download: пришли заголовки, статус 200
[3.10с] download: страница получена, ... байт  <<< КОНТЕКСТ ВЕРНУЛСЯ СЮДА
```

Смотри, что произошло: `download` дошёл до `await` на ответ сервера, **заморозился
и отдал loop'у управление**. Loop не простаивал — он крутил `blinker` и печатал
тики. Сокет всё это время ждал в `epoll`. Как только страница отдалась, ОС
разбудила сокет, loop **возобновил `download` ровно с того `await`**, и корутина
допечатала результат. Один поток, никакого параллелизма — а работа шла вперемешку.

# Часть 7. Запускаем много корутин

Инструменты, чтобы дирижировать пачкой корутин:

- **`asyncio.gather(*coros)`** — запустить все, дождаться всех, вернуть список
  результатов **в порядке аргументов**. Падение одной по умолчанию роняет
  gather; `return_exceptions=True` — вернёт исключения как обычные значения.
- **`asyncio.create_task(coro)`** — запланировать корутину в фон и продолжить;
  результат забрать позже через `await task`. Так делают «фоновую работу».
- **`asyncio.as_completed(coros)`** — итерируешь и получаешь результаты **по мере
  готовности**, а не в порядке запуска. Удобно печатать «готово!» сразу.
- **`asyncio.Semaphore(n)`** — ограничитель: не больше `n` корутин в критической
  секции одновременно. Классический **backpressure**: не выпускай 10 000 сокетов
  разом — упрёшься в лимиты ОС и разозлишь сервер. `async with semaphore:` вокруг
  запроса — и в полёте максимум `n`. Это ты применишь в практике.

```python
sem = asyncio.Semaphore(5)                # не больше 5 запросов разом

async def fetch(session, url):
    async with sem:                       # 6-й подождёт, пока освободится слот
        async with session.get(url) as r:
            return await r.read()
```

# Часть 8. Ловушка блокировки и общий рецепт

Файлы: [03_blocking_vs_await.py](03_blocking_vs_await.py),
[06_run_in_executor.py](06_run_in_executor.py)

## Ловушка №1: блокирующий вызов в async-коде вешает весь loop

Демо `03` показывает это в лоб. Есть `ticker`, который тикает каждые 0.2 с — это
«пульс» приложения. Рядом — воркер:

- воркер с `await asyncio.sleep(1)` — тики идут **ровно**: воркер отдал
  управление, loop свободен;
- воркер с `time.sleep(1)` — тики **замирают на секунду**: `time.sleep` —
  синхронный блокирующий вызов, он не отдаёт управление, и весь loop стоит.

`time.sleep` тут — модель **любого** блокирующего вызова: `requests.get`,
`psycopg2`, `open().read()` большого файла, `hashlib` на гигабайте. Внутри
`async def` любой из них морозит всё приложение. Правило: **в `async def` всё,
что долго, должно быть `await`, а не блокирующим вызовом.**

## Рецепт: три категории внешних вызовов

**1. Есть нативный async-клиент (лучший случай).** Просто бери его:

- HTTP: `aiohttp` или `httpx.AsyncClient` вместо `requests`
- Postgres: `asyncpg` / SQLAlchemy async вместо `psycopg2`
- MySQL: `aiomysql` / `asyncmy`; MongoDB: `motor`; Redis: `redis.asyncio`

Если для ресурса есть async-нативная библиотека — вопрос закрыт, костыли не нужны.

**2. Async-клиента нет, а синхронная блокирующая библиотека есть.** Уводи
блокирующий вызов в **отдельный поток** через `run_in_executor`:

```python
import asyncio

async def call_blocking_lib():
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(
        None,               # None = дефолтный ThreadPoolExecutor
        blocking_function,  # синхронная функция
        arg1, arg2,         # её аргументы
    )
    return result
```

Что происходит: `run_in_executor` кидает `blocking_function` в пул потоков и
возвращает корутине Future; корутина `await`'ит его — то есть **отдаёт управление
loop'у**, пока где-то в фоне поток блокируется на синхронном вызове. Поток
закончил — Future резолвится — корутина продолжается. GIL здесь не помеха: пока
поток стоит в `recv()` (вне Python-байткода, замок отпущен), главный поток с
event loop'ом спокойно крутит другие корутины. Это демо `06`, часть с потоком.

> Кстати, FastAPI делает это автоматически для **синхронных** `def`-эндпоинтов
> (уводит их в `run_in_threadpool`), но **не** для блокирующего вызова *внутри*
> `async def` — там ты сам. Практический вывод из B4: зовёшь блокирующую
> библиотеку и не хочешь возиться — объяви эндпоинт обычным `def`. Объявил
> `async def` — всё внутри обязано быть неблокирующим.

**3. CPU-bound работа (не I/O, а реальные вычисления).** Тут поток **не
поможет** — он будет занимать ядро и держать GIL всё время расчёта, и loop опять
встанет. Нужен **процесс** через `ProcessPoolExecutor`:

```python
from concurrent.futures import ProcessPoolExecutor

async def cpu_heavy_call():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, heavy_computation, data)
    return result
```

Расчёт уходит в **отдельный интерпретатор со своим GIL** на другом ядре; наш loop
всё это время свободен. Это демо `06`, часть с процессом (на Windows её надо
запускать прямым `python 06_run_in_executor.py` — почему, объяснено в самом файле:
дочерний процесс через spawn заново импортирует модуль).

### Резюме-таблица

| Тип ресурса | Решение | Почему loop не блокируется |
|---|---|---|
| БД/HTTP с async-драйвером | `asyncpg`, `aiohttp` | неблокирующий сокет + интеграция с `epoll` |
| Блокирующая либа без async | `run_in_executor` + **поток** | блокировка ушла в отдельный поток, loop свободен |
| CPU-bound вычисления | `run_in_executor` + **процесс** | расчёт ушёл в отдельный процесс, свой GIL |

**Итог одной фразой:** event loop даёт конкурентность на одном потоке за счёт
`await` в точках I/O; GIL мешает параллелить *CPU*-работу потоками. Async быстр,
пока ты **не блокируешь loop** — для I/O бери async-клиенты, для блокирующего и
CPU-кода уводи работу в пул потоков/процессов.

# Часть 9. Частые ошибки

- **Забыл `await`.** `session.get(url)` без `await` — это корутина/контекст-
  менеджер, а не ответ. Симптом: `RuntimeWarning: coroutine was never awaited`
  или странный объект вместо данных.
- **Блокирующий вызов в `async def`.** `requests.get`, `time.sleep`, `psycopg2`,
  тяжёлый цикл — вешают весь loop (часть 8). Признак: «async, а всё равно
  тормозит и всё встаёт».
- **`ClientSession` на каждый запрос.** Теряешь пул соединений, течёшь сокетами.
  Одна сессия на приложение/на пачку задач.
- **`gather` на десятки тысяч задач без семафора.** Упрёшься в лимит открытых
  файлов/сокетов ОС или в rate-limit сервера. Ограничивай `Semaphore`.
- **Смешал sync и async бездумно.** `asyncio.run()` нельзя звать из уже
  запущенного loop; корутину нельзя запустить обычным вызовом. Держи в голове
  границу «синхронный мир ↔ асинхронный мир»: переход — только `asyncio.run`
  (внутрь) и `run_in_executor` (наружу, к блокирующему коду).
