# Урок B4. Основы FastAPI: HTTP, REST, эндпоинты, первое приложение, роуты

В B3 мы научились ходить в чужие сайты `requests`-ом и парсить ответ. Теперь
переворачиваем картинку: будем не **клиентом**, который запрашивает, а
**сервером**, который отвечает. Пишем собственный веб-API на **FastAPI** —
современном Python-фреймворке, на котором сегодня делают бэкенды в проде.

Урок состоит из двух частей:

- **Теория** — что такое HTTP, REST, эндпоинт; как поднять первое приложение и
  раздать роуты. Плюс отдельный теоретический блок про **event loop и GIL** —
  почему FastAPI асинхронный и что под этим лежит.
- **Разбор готового приложения** — мы притащили целиком бэкенд реального
  тестового задания ([backend/](backend/)): регистрация, JWT-авторизация,
  пользователи и статьи, PostgreSQL через async-драйвер. На нём смотрим, как
  теория выглядит в боевом коде.

Главная мысль урока: **API — это контракт**. URL говорит «над каким ресурсом»,
HTTP-метод — «что с ним сделать», тело запроса — «с какими данными», код
ответа — «чем кончилось». FastAPI всего лишь помогает этот контракт описать и
заставить его соблюдаться.

# Часть 1. Теория

## 1. HTTP — как клиент и сервер разговаривают

**HTTP** (HyperText Transfer Protocol) — текстовый протокол «запрос-ответ».
Клиент (браузер, мобильное приложение, твой `requests`) шлёт **запрос**, сервер
возвращает **ответ**. Одно соединение — один цикл «спросил -> ответили». Сервер
сам ничего не инициирует.

### Анатомия запроса

```
POST /users HTTP/1.1                 <- стартовая строка: МЕТОД, путь, версия
Host: api.example.com                <- заголовки (метаданные)
Content-Type: application/json
Authorization: Bearer eyJhbGci...
                                     <- пустая строка отделяет заголовки от тела
{"first_name": "Иван", "email": "i@x.ru"}   <- тело (body), есть не у всех запросов
```

Четыре части, которые надо различать:

- **Метод** — что делаем (см. ниже).
- **Путь (URL)** — над чем делаем: `/users/42`.
- **Заголовки** — служебная информация: формат тела (`Content-Type`), токен
  авторизации (`Authorization`), что клиент готов принять (`Accept`).
- **Тело** — данные, которые шлём на сервер. Есть у `POST`/`PUT`/`PATCH`,
  обычно **нет** у `GET`/`DELETE`.

### Анатомия ответа

```
HTTP/1.1 201 Created                 <- версия, КОД статуса, текст
Content-Type: application/json

{"id": 42, "first_name": "Иван"}     <- тело ответа
```

### HTTP-методы (глаголы)

| Метод    | Смысл                       | Тело | Идемпотентность* |
|----------|-----------------------------|------|------------------|
| `GET`    | прочитать ресурс            | нет  | да               |
| `POST`   | создать новый ресурс        | да   | нет              |
| `PUT`    | заменить ресурс целиком     | да   | да               |
| `PATCH`  | изменить ресурс частично    | да   | нет (обычно)     |
| `DELETE` | удалить ресурс              | нет  | да               |

\* **Идемпотентность** — повторил тот же запрос дважды, результат на сервере тот
же, что и после одного. `DELETE /users/42` дважды — пользователь всё так же
удалён (второй раз вернёт 404, но состояние не изменится). А `POST /users`
дважды — это **два** пользователя. Поэтому создание — это `POST`, а не `PUT`.

### Коды статуса (чем кончилось)

Цифра сотен задаёт класс ответа:

- **2xx — успех.** `200 OK` (всё ок, есть тело), `201 Created` (создан ресурс),
  `204 No Content` (ок, тела нет — типично для `DELETE`).
- **3xx — перенаправление.** `301`/`302` (редирект), `304 Not Modified` (кэш).
- **4xx — ошибка клиента** (сам виноват). `400 Bad Request` (кривой запрос),
  `401 Unauthorized` (не залогинен), `403 Forbidden` (залогинен, но нельзя),
  `404 Not Found` (нет такого), `409 Conflict` (конфликт, напр. email занят),
  `422 Unprocessable Entity` (тело не прошло валидацию — **код FastAPI по
  умолчанию** при ошибке pydantic).
- **5xx — ошибка сервера** (сервер виноват). `500 Internal Server Error`,
  `502 Bad Gateway`, `503 Service Unavailable`.

Запомни разницу `401` vs `403`: 401 — «не знаю, кто ты, предъяви токен», 403 —
«знаю, кто ты, но тебе сюда нельзя». В нашем примере это видно в [handlers/users.py](backend/source/handlers/users.py):
чужой профиль обычному пользователю -> `403`, а несуществующий пользователь -> `404`.

## 2. REST — стиль проектирования API

**REST** — это не протокол и не библиотека, а **набор соглашений**, как строить
HTTP-API, чтобы он был предсказуемым. Главные правила:

**1. Ресурс — это существительное, в URL — множественное число.**

```
/users          /users/42          /articles          /articles/7
```

URL **называет вещь**, а не действие. Плохо: `/getUser?id=42`, `/createUser`.
Хорошо: `/users/42` (а что с ним делать — скажет метод).

**2. Действие — это HTTP-метод, а не часть URL.**

| Хочу                          | REST-способ              |
|-------------------------------|--------------------------|
| список пользователей          | `GET /users`             |
| одного пользователя           | `GET /users/42`          |
| создать пользователя          | `POST /users`            |
| заменить пользователя         | `PUT /users/42`          |
| удалить пользователя          | `DELETE /users/42`       |
| статьи (вложенный ресурс)     | `GET /users/42/articles` |

Один и тот же URL `/users/42` обслуживает чтение, замену и удаление — различает
их **метод**. Ровно это видно в [routers/users.py](backend/source/routers/users.py):
`@router.get("/{user_id}")`, `@router.put("/{user_id}")`, `@router.delete("/{user_id}")`.

**3. Сервер без состояния (stateless).** Каждый запрос самодостаточен: сервер не
помнит «прошлый раз ты залогинился». Поэтому токен/куку шлют **в каждом** запросе
(в нашем примере — `access_token` в куке, читается в каждом хендлере).

**4. Внятные коды ответа.** Создал -> `201`, не нашёл -> `404`, нет прав -> `403`.
Не «200 с полем `{"error": true}` внутри» — код статуса и есть результат.

REST не догма (бывает оправданно отойти), но если сомневаешься — делай по REST,
тебя поймёт любой другой разработчик и любой инструмент (Swagger, Postman).

## 3. Эндпоинт — что это

**Эндпоинт (endpoint)** — это конкретная пара **`метод + путь`**, которую сервер
умеет обрабатывать, вместе с привязанной к ней функцией.

```
POST /auth/sign-up      -> функция sign_up()
GET  /users/{user_id}   -> функция get_user()
```

`GET /users/42` и `POST /users` — это **два разных эндпоинта**, хотя путь общий.
Эндпоинт — это «дверь» в твоё приложение: снаружи видны только метод и URL, что
за ними — клиента не касается.

В FastAPI один эндпоинт — это обычно одна функция с декоратором:

```python
@router.get("/{user_id}")          # метод GET + путь /{user_id}
async def get_user(user_id: int):  # функция-обработчик этого эндпоинта
    ...
```

Совокупность всех эндпоинтов и есть твой **API**. FastAPI по ним автоматически
строит интерактивную документацию (Swagger UI на `/docs`) — список всех дверей с
описанием, какие данные принимают и возвращают.

## 4. Первое приложение на FastAPI

Минимальное рабочее приложение — буквально пять строк. Это та основа, поверх
которой надстроен весь наш [backend/](backend/):

```python
# hello.py
from fastapi import FastAPI

app = FastAPI()              # объект приложения — сердце FastAPI

@app.get("/")               # эндпоинт: GET на корень
def read_root():
    return {"message": "Привет, API!"}   # dict -> FastAPI сам отдаст как JSON
```

Запуск через ASGI-сервер **uvicorn**:

```bash
pip install fastapi "uvicorn[standard]"
uvicorn hello:app --reload      # hello = имя файла, app = имя объекта
```

`--reload` перезапускает сервер при изменении кода (только для разработки).
Открываешь:

- `http://127.0.0.1:8000/` — увидишь `{"message": "Привет, API!"}`;
- `http://127.0.0.1:8000/docs` — **Swagger UI**, готовая документация, прямо из
  браузера можно дёргать эндпоинты;
- `http://127.0.0.1:8000/redoc` — альтернативная документация.

Откуда документация? FastAPI читает **аннотации типов** твоих функций и
pydantic-схемы и по ним генерирует OpenAPI-спецификацию. Поэтому типы здесь — не
украшение, а источник и валидации, и доков.

В нашем примере приложение создаётся в [backend/main.py](backend/main.py):

```python
app = FastAPI(title="Test Task API")

@app.on_event("startup")          # хук: выполнить при старте
async def open_connection():
    await connect_with_retry()    # подключаемся к БД, создаём таблицы

app.include_router(auth_router, prefix="/auth", tags=["Auth"])
app.include_router(users_router, prefix="/users", tags=["Users"])
app.include_router(articles_router, prefix="/articles", tags=["Articles"])

if __name__ == "__main__":
    uvicorn.run(app, host=settings.APP_HOST, port=settings.APP_PORT)
```

Здесь добавились две вещи поверх «hello»: **хуки жизненного цикла**
(`startup`/`shutdown` — открыть/закрыть соединение с БД) и **подключение
роутеров** через `include_router`. Про роутеры — дальше.

## 5. Роуты — маршрутизация запросов

**Роутинг** — это сопоставление «пришёл `метод + путь` -> вызвать вот эту
функцию». В FastAPI роут объявляется декоратором над функцией.

### Параметры пути (path parameters)

Кусок URL в фигурных скобках — это переменная, она прилетает в функцию
аргументом. Аннотация типа задаёт и преобразование, и валидацию:

```python
@router.get("/{user_id}")
async def get_user(user_id: int):      # /users/42 -> user_id = 42 (int)
    ...
```

`/users/abc` сюда не пройдёт — FastAPI увидит, что `abc` не `int`, и сам вернёт
`422` ещё до входа в функцию. Бесплатная защита от мусора на входе.

### Параметры запроса (query parameters)

Аргумент функции, которого **нет** в пути, FastAPI ищет в query-строке
(`?limit=10&offset=0`):

```python
@router.get("/articles")
async def list_articles(limit: int = 20, offset: int = 0):   # /articles?limit=5
    ...
```

Есть значение по умолчанию -> параметр необязательный; нет -> обязательный.

### Тело запроса (request body) и pydantic

Данные на создание/изменение шлют в теле JSON-ом. Описываешь форму тела
**pydantic-схемой**, и FastAPI сам распарсит, проверит типы и подставит готовый
объект. Смотри [schemas/auth.py](backend/source/schemas/auth.py):

```python
from pydantic import BaseModel, EmailStr

class SignUpRequest(BaseModel):
    first_name: str
    last_name: str
    middle_name: str | None = None    # необязательное поле
    email: EmailStr                   # валидирует, что это похоже на email
    password: str
    password_confirm: str
```

И сам эндпоинт ([routers/auth.py](backend/source/routers/auth.py)):

```python
@router.post("/sign-up")
async def sign_up(body: SignUpRequest, response: Response):
    result = await auth_handler.sign_up(body, response)
    ...
```

Аргумент `body: SignUpRequest` — FastAPI понимает: «это тело запроса». Если
прислали JSON без `email` или с числом вместо строки — клиент получит `422` с
подробным описанием, **какое именно поле кривое**, и до тела функции дело не
дойдёт. Валидация бесплатно.

### `response_model` — контракт ответа

Можно задать схему и для **ответа**. FastAPI отфильтрует лишние поля и проверит
форму отдаваемого. Так в [routers/users.py](backend/source/routers/users.py)
`response_model=UserResponse` гарантирует, что наружу не утечёт `password_hash`,
даже если он есть в объекте модели:

```python
@router.get("/{user_id}", response_model=UserResponse)
async def get_user(user_id: int, request: Request):
    ...
```

### APIRouter — дробим приложение на модули

Складывать сто эндпоинтов в один `main.py` нельзя. **`APIRouter`** — это
мини-приложение: группа роутов в отдельном файле, которую потом целиком
подключают к главному `app`.

```python
# routers/users.py
from fastapi import APIRouter
router = APIRouter()

@router.get("/{user_id}")
async def get_user(user_id: int):
    ...
```

```python
# main.py
app.include_router(users_router, prefix="/users", tags=["Users"])
```

`prefix="/users"` приклеивается ко всем путям роутера: `@router.get("/{user_id}")`
превращается в эндпоинт `GET /users/{user_id}`. `tags=["Users"]` — группировка в
Swagger. Итог: каждый ресурс (`auth`, `users`, `articles`) живёт в своём файле,
а `main.py` лишь собирает их вместе. Это и есть скелет любого FastAPI-проекта.

### Поток одного запроса целиком

На примере `POST /auth/sign-up` видно всю цепочку слоёв нашего бэкенда:

```
HTTP-запрос  POST /auth/sign-up  + JSON-тело
   │
   ▼
main.py            include_router -> отдал в auth_router
   │
   ▼
routers/auth.py    нашёл эндпоинт, провалидировал тело в SignUpRequest
   │
   ▼
handlers/auth.py   бизнес-логика: проверил пароли, сходил в БД, создал юзера
   │
   ▼
models/user.py     ORM-объект -> строка в таблице users
   │
   ▼
HTTP-ответ   200 + {"message": "Registered successfully"} + кука с токеном
```

Разделение «роутер (маршрут) -> хендлер (логика) -> модель (данные)» — не
требование FastAPI, а здоровая привычка: роутер остаётся тонким, логика
тестируема, и каждый слой занят своим делом.

# Часть 2. Event loop и GIL — почему FastAPI асинхронный

Ты заметил `async def` у эндпоинтов. Это не для красоты. FastAPI построен на
**asyncio**, и чтобы он держал тысячи одновременных подключений на одном потоке,
важно понимать, что под капотом. Здесь два связанных, но **разных** понятия —
event loop и GIL. Их постоянно путают.

## GIL в двух словах

**GIL** (Global Interpreter Lock) — глобальный замок интерпретатора CPython:
в любой момент времени **байткод Python выполняет только один поток**, даже если
у тебя 16 ядер. Потоки в Python переключаются, но не выполняются по-настоящему
параллельно (до free-threaded сборки 3.13+).

Важный нюанс: GIL **отпускается** на время блокирующих syscall'ов (чтение файла,
ожидание сети) — C-расширение может сказать «я ушёл ждать I/O, замок свободен,
пусть другой поток покрутится». Поэтому потоки в Python хороши для I/O-bound
задач и почти бесполезны для CPU-bound.

## Event loop в двух словах

**Event loop** — это **один поток**, который крутит много корутин по очереди,
переключаясь между ними в точках `await`. Никакого параллелизма: пока одна
корутина считает что-то на CPU, остальные ждут. Выигрыш в другом — когда корутина
доходит до `await` на I/O (запрос в БД, в сеть), она **отдаёт управление**
циклу, и тот идёт обслуживать другие корутины, пока ответ не придёт.

Ключевое отличие от потоков: переключение между корутинами происходит **только
в точках `await`**, явно и предсказуемо, а не в произвольный момент, как у
потоков. Один поток — значит GIL тут вообще не при делах.

И вот тут начинается главная ловушка новичка: **блокирующий вызов внутри
`async def` вешает весь event loop**. Разберём почему, на примере похода в БД.

### Синхронный драйвер: что происходит под капотом

Когда `psycopg2` делает `cursor.execute("SELECT ...")`, происходит это:

1. Python-код вызывает C-функцию драйвера
2. Драйвер делает системный вызов `send()` на сокет — отправляет запрос в Postgres
3. Драйвер делает `recv()` — и тут блокируется. ОС переводит этот поток в состояние "ожидание I/O", поток не потребляет CPU, но и не возвращает управление вызывающему коду
4. Только когда Postgres ответит, `recv()` возвращается, и Python-код продолжается

Ключевое: шаги 2-3 — это **блокирующий syscall**. С точки зрения event loop'а (который живёт в том же потоке), весь этот промежуток — чёрная дыра. Loop не может туда заглянуть, не может ничего переключить, потому что поток физически занят ожиданием внутри C-функции, а не выполняет Python-байткод, который loop мог бы прервать в точке `await`.

Заметь — GIL тут даже не главный затык. Драйвер мог бы отпустить GIL во время `recv()` (многие C-расширения это делают, чтобы не блокировать _другие_ потоки) — но это не помогает asyncio, потому что у тебя всего один поток в event loop, и это не про GIL, а про то, что нет точки `await`/`yield`, чтобы loop переключился на другую корутину.

### Асинхронный драйвер (`asyncpg`): что происходит под капотом

1. `await conn.fetch("SELECT ...")` вызывается
2. Внутри `asyncpg` сокет переведён в неблокирующий режим (`socket.setblocking(False)`)
3. Драйвер пытается `send()` — если буфер сокета не готов принять данные, вместо блокировки происходит `await` на специальный Future, который зарегистрирован в event loop через `add_writer`/`add_reader` (это используя `selectors`/`epoll`/`kqueue` под капотом — то, на чём построен сам asyncio event loop)
4. Корутина "замораживается" в этой точке, управление возвращается в event loop
5. Loop идёт обслуживать другие готовые к выполнению корутины
6. Когда ОС через `epoll` сигналит "сокет готов на чтение" — event loop возобновляет именно эту корутину с того места, где она остановилась

Грубо: `asyncpg` сам реализует протокол Postgres (бинарный wire protocol) на чистом Python/Cython поверх неблокирующих сокетов, интегрированных с тем же `epoll`, на котором крутится весь твой event loop. Поэтому ожидание ответа от БД — это не блокировка потока, а просто "я зарегистрировал интерес к этому сокету, проснусь, когда будет готово".

Именно поэтому в нашем примере БД-драйвер — **`asyncpg`** (см. [requirements.txt](backend/requirements.txt) и URL `postgresql+asyncpg://...` в [config.py](backend/source/config.py)), а все хендлеры делают `await session.get(...)` / `await session.commit()`. Ни один поход в БД не вешает loop.

### Как работать с "внешними штуками" не блокируя loop — общий рецепт

Есть три категории внешних вызовов, и для каждой свой путь:

**1. Есть нативный async-клиент (лучший случай)**

- БД: `asyncpg` (Postgres), `aiomysql`/`asyncmy` (MySQL), `motor` (MongoDB)
- HTTP: `httpx.AsyncClient` или `aiohttp` вместо `requests`
- Redis: `redis.asyncio`

Правило простое: если для твоего "внешнего ресурса" есть async-нативная библиотека — используй её, никаких костылей не нужно.

**2. Нативного async-клиента нет, а синхронная блокирующая библиотека есть**

Тогда уводишь блокирующий вызов в отдельный поток через `run_in_executor`, чтобы он не вис на event loop:

```python
import asyncio

async def call_blocking_lib():
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(
        None,  # дефолтный ThreadPoolExecutor
        blocking_function,  # синхронная функция
        arg1, arg2
    )
    return result
```

Что происходит: `run_in_executor` кидает `blocking_function` в пул потоков, возвращает корутине Future, корутина на этом Future делает `await` — то есть отдаёт управление event loop'у, пока поток где-то в фоне блокируется на синхронном вызове. Когда поток закончит — Future резолвится, корутина продолжается.

Важный нюанс: GIL здесь снова не помеха, потому что пока один поток блокирован в `recv()` (вне Python-байткода, GIL отпущен на время syscall), главный поток с event loop'ом спокойно крутит другие корутины — он-то Python-байткод выполняет, GIL у него свободен.

FastAPI, кстати, делает это автоматически для синхронных `def`-эндпоинтов (через `run_in_threadpool`), но не для блокирующего вызова **внутри** `async def` — там придётся самому. Практический вывод: если эндпоинт зовёт блокирующую библиотеку и ты не хочешь возиться — объяви его обычным `def`, FastAPI сам уведёт его в пул потоков. А если объявил `async def` — всё внутри обязано быть неблокирующим.

**3. CPU-bound работа (не I/O, а реальные вычисления)**

Тут `run_in_executor` с потоками не поможет — поток будет занимать CPU и держать GIL во время вычислений (без free-threaded сборки). Нужен `ProcessPoolExecutor` вместо `ThreadPoolExecutor`:

```python
from concurrent.futures import ProcessPoolExecutor

async def cpu_heavy_call():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, heavy_computation, data)
    return result
```

### Резюме-таблица

| Тип ресурса | Решение | Почему loop не блокируется |
|---|---|---|
| БД с async-драйвером | `asyncpg` и т.п. | Неблокирующий сокет + интеграция с epoll |
| БД/HTTP без async-драйвера | `run_in_executor` + поток | Блокировка уходит в отдельный поток, event loop свободен |
| CPU-bound вычисления | `run_in_executor` + процесс | Вычисление уходит в отдельный процесс, не делит GIL с main |

**Итог одной фразой:** event loop даёт конкурентность на одном потоке за счёт
`await` в точках I/O; GIL мешает параллелить CPU-работу потоками. FastAPI быстрый,
пока ты **не блокируешь loop** — для I/O бери async-клиенты, для блокирующего и
CPU-кода уводи работу в пул потоков/процессов.

# Как запустить пример

Готовый бэкенд из [backend/](backend/) поднимается одной командой через Docker
(вместе с PostgreSQL). Нужны установленные Docker и Docker Compose.

   ```bash
   cp .env-example .env
   ```

   `SEED_DB=true` заполнит базу тестовыми пользователями и статьями при старте.

2. Собери и запусти:

   ```bash
   docker compose build
   docker compose up
   ```

3. Открой **Swagger UI**: `http://localhost:8000/docs` — там видны все эндпоинты
   (`/auth/sign-up`, `/auth/sign-in`, `/users/{user_id}`, `/articles` ...), их
   можно дёргать прямо из браузера.

| Email | Пароль | Роль |
|---|---|---|
| admin@example.com | admin123 | Администратор |
| user2@example.com | user123 | Пользователь |

[main.py](backend/main.py) -> [routers/users.py](backend/source/routers/users.py)
-> [handlers/users.py](backend/source/handlers/users.py) ->
[schemas/user.py](backend/source/schemas/user.py). Это вертикальный срез одного
ресурса: маршрут, логика, форма данных.
