# Урок B2. FastAPI: первое приложение, роуты и разделение на слои

В L6 мы были **клиентом** — ходили в чужие сайты и парсили ответ. Теперь
становимся **сервером**, который отвечает: пишем веб-API на **FastAPI**.

Это намеренно **маленький** урок без БД и без Docker — чтобы ничего не отвлекало
от двух главных вещей:

1. **Как устроен HTTP-API** — методы, роуты, схемы запроса/ответа, коды статусов.
2. **Как разложить код по слоям** — `main` -> роутеры -> хендлеры -> сервисы ->
   модели/схемы. Это скелет, который потом масштабируется до большого проекта
   (его боевой пример — в соседнем уроке B4).

Приложение — крошечный сервис «users»: пара `GET`-методов отдаёт статические
модели, `POST` принимает модель и возвращает созданную. Никакой базы — вместо неё
заранее заданный список объектов в памяти. Цель — не данные, а **архитектура**.

В конце — теоретический блок про **event loop и GIL** (почему у эндпоинтов
`async def`), а практическое задание вынесено в отдельный файл [to-do.md](to-do.md).

# Часть 1. Базовые понятия

## HTTP в двух абзацах

**HTTP** — протокол «запрос-ответ». Клиент шлёт **запрос**, сервер возвращает
**ответ**. В запросе важны четыре вещи:

- **метод** — что делаем: `GET` (прочитать), `POST` (создать), `PUT`/`PATCH`
  (изменить), `DELETE` (удалить);
- **путь (URL)** — над чем делаем: `/users/2`;
- **заголовки** — метаданные (формат тела, токен авторизации);
- **тело** — данные (JSON у `POST`/`PUT`; у `GET`/`DELETE` обычно нет).

В ответе главное — **код статуса**: `2xx` успех (`200 OK`, `201 Created`),
`4xx` ошибка клиента (`404` нет ресурса, `422` тело не прошло валидацию — код
FastAPI по умолчанию), `5xx` ошибка сервера (`500`).

## REST — соглашения об URL

**REST** — это договорённости, как называть эндпоинты, чтобы их понимал любой:

- ресурс — **существительное во множественном числе**: `/users`, `/users/2`;
- действие — это **метод**, а не часть URL (не `/getUser`, а `GET /users/2`);
- один URL обслуживает разные действия через метод: `GET /users/2` (прочитать),
  `POST /users` (создать), `DELETE /users/2` (удалить);
- результат — это **код ответа**, а не поле `{"error": ...}` в теле.

**Эндпоинт** — конкретная пара `метод + путь` и привязанная к ней функция.
`GET /users` и `POST /users` — два разных эндпоинта с общим URL.

## Первое приложение

Минимальный FastAPI — три значимые строки:

```python
from fastapi import FastAPI

app = FastAPI()                # объект приложения

@app.get("/")                  # эндпоинт: GET на корень
def root():
    return {"message": "Привет"}   # dict -> FastAPI сам отдаст JSON-ом
```

Запуск ASGI-сервером uvicorn: `uvicorn main:app --reload` (`main` — имя файла,
`app` — имя объекта). FastAPI читает аннотации типов и pydantic-схемы и по ним
сам строит и **валидацию**, и **документацию** на `/docs`.

## Роуты

**Роут** — правило «пришёл `метод + путь` -> вызвать эту функцию». Объявляется
декоратором. См. [source/routers/users.py](source/routers/users.py):

```python
@router.get("/{user_id}", response_model=UserResponse)
async def get_user(user_id: int):       # /users/2 -> user_id = 2 (int)
    ...
```

- **Параметр пути** `{user_id}` прилетает в функцию аргументом; аннотация `int`
  и валидирует (`/users/abc` -> сразу `422`), и преобразует тип.
- **Тело запроса** описывают pydantic-схемой — FastAPI распарсит и проверит:

  ```python
  @router.post("", response_model=UserResponse, status_code=201)
  async def create_user(body: UserCreate):   # body — провалидированное тело
      ...
  ```

- **`response_model`** задаёт форму ответа: FastAPI отфильтрует лишние поля и
  проверит, что отдаём именно то, что обещали.
- **`APIRouter`** — группа роутов одного ресурса в отдельном файле; `main.py`
  подключает её целиком: `app.include_router(users_router, prefix="/users")`.
  Префикс приклеивается ко всем путям роутера.

# Часть 2. Разделение на слои (главное в уроке)

Можно было сложить все три эндпоинта в один `main.py` — и для трёх работает. Но
как только проект растёт, такой файл превращается в кашу: HTTP, бизнес-правила и
доступ к данным перемешаны, ничего не протестировать по отдельности. Поэтому код
режут на **слои**, у каждого одна ответственность. Запрос проходит сквозь них
сверху вниз, ответ — снизу вверх:

```
HTTP-запрос
   │
   ▼
main.py        создаёт app, подключает роутеры, запускает сервер
   │
   ▼
routers/       РОУТ: метод+путь -> функция. Разбирает HTTP, валидирует тело/путь
   │           по схемам. Логики нет.            (source/routers/users.py)
   ▼
handlers/      ХЕНДЛЕР: бизнес-логика. Решает, что делать, бросает 404/403.
   │           Не знает про URL, не лезет в данные напрямую. (source/handlers/users.py)
   ▼
services/      СЕРВИС: работа с данными. В проде — поход в БД; у нас — статика.
   │           Оперирует моделями.                (source/services/users.py)
   ▼
models/        МОДЕЛЬ: доменный объект (dataclass / ORM-строка). (source/models/user.py)
schemas/       СХЕМА: pydantic-форма запроса и ответа на границе HTTP. (source/schemas/user.py)
   │
   ▼
HTTP-ответ
```

### Кто за что отвечает

| Слой | Файл | Ответственность | Что НЕ его дело |
|---|---|---|---|
| `main` | [main.py](main.py) | создать `app`, подключить роутеры, запуск | бизнес-логика |
| `routers` | [source/routers/users.py](source/routers/users.py) | метод+путь -> хендлер, схемы вход/выход | сами данные, правила |
| `handlers` | [source/handlers/users.py](source/handlers/users.py) | решения, HTTP-ошибки, оркестрация | URL, прямой доступ к данным |
| `services` | [source/services/users.py](source/services/users.py) | достать/сохранить данные | HTTP, коды ответов |
| `models` | [source/models/user.py](source/models/user.py) | доменная сущность + статические данные | HTTP, валидация ввода |
| `schemas` | [source/schemas/user.py](source/schemas/user.py) | форма JSON на входе/выходе | логика, хранение |

### Модель против схемы — частый вопрос

Их два разных, и это нарочно:

- **Модель** (`models/`) — внутренняя сущность, как данные живут в приложении/БД.
- **Схема** (`schemas/`) — что видит клиент снаружи (тело запроса, тело ответа).

Зачем разделять: чтобы наружу не утекало лишнее. Классика — у модели `User` есть
`password_hash`, а в `UserResponse` его нет, и он физически не может попасть в
ответ. В нашем уроке схема `UserCreate` (вход) намеренно **не содержит `id`** —
его выдаёт сервер, клиент его не присылает; а `UserResponse` (выход) `id` уже
содержит.

### Почему это окупается

- **Тестируемость**: хендлер можно проверить, подсунув фейковый сервис, без
  поднятия HTTP-сервера.
- **Замена слоя без боли**: сегодня сервис отдаёт статику из памяти, завтра —
  ходит в PostgreSQL. Меняется только `services/`, роутеры и хендлеры не трогаем.
- **Понятность**: где искать? Кривой URL — в роутер. Неверное правило доступа —
  в хендлер. Не так достаются данные — в сервис. Каждому багу — свой слой.

Это ровно та же раскладка, что в большом боевом приложении из урока B4 — там
поверх неё навешаны БД, JWT-авторизация и права доступа.

# Часть 3. Event loop и GIL — почему эндпоинты `async def`

Ты заметил `async def` у эндпоинтов, хендлеров и сервисов. Это не для красоты:
FastAPI построен на **asyncio**, и чтобы держать тысячи одновременных соединений
на одном потоке, важно понимать, что под капотом. Тут два связанных, но **разных**
понятия — event loop и GIL. Их постоянно путают.

## GIL в двух словах

**GIL** (Global Interpreter Lock) — глобальный замок интерпретатора CPython:
в любой момент байткод Python выполняет **только один поток**, даже на 16 ядрах.
Потоки переключаются, но не работают по-настоящему параллельно (до free-threaded
сборки 3.13+).

Нюанс: GIL **отпускается** на время блокирующих syscall'ов (чтение файла,
ожидание сети) — C-расширение говорит «я ушёл ждать I/O, замок свободен». Поэтому
потоки хороши для I/O-bound и почти бесполезны для CPU-bound.

## Event loop в двух словах

**Event loop** — это **один поток**, который крутит много корутин по очереди,
переключаясь между ними в точках `await`. Параллелизма нет. Выигрыш в другом:
когда корутина доходит до `await` на I/O (запрос в БД, в сеть), она **отдаёт
управление** циклу, и тот идёт обслуживать другие корутины, пока ответ не придёт.
Переключение происходит **только в точках `await`** — явно и предсказуемо, не как
у потоков. Один поток — значит GIL тут вообще не при делах.

И вот главная ловушка новичка: **блокирующий вызов внутри `async def` вешает весь
event loop**. Разберём почему, на примере похода в БД.

### Синхронный драйвер: что происходит под капотом

Когда `psycopg2` делает `cursor.execute("SELECT ...")`, происходит это:

1. Python-код вызывает C-функцию драйвера
2. Драйвер делает системный вызов `send()` на сокет — отправляет запрос в Postgres
3. Драйвер делает `recv()` — и тут блокируется. ОС переводит этот поток в состояние "ожидание I/O", поток не потребляет CPU, но и не возвращает управление вызывающему коду
4. Только когда Postgres ответит, `recv()` возвращается, и Python-код продолжается

Ключевое: шаги 2-3 — это **блокирующий syscall**. С точки зрения event loop'а (который живёт в том же потоке), весь этот промежуток — чёрная дыра. Loop не может туда заглянуть, не может ничего переключить, потому что поток физически занят ожиданием внутри C-функции, а не выполняет Python-байткод, который loop мог бы прервать в точке `await`.

Заметь — GIL тут даже не главный затык. Драйвер мог бы отпустить GIL во время `recv()` (многие C-расширения это делают, чтобы не блокировать _другие_ потоки) — но это не помогает asyncio, потому что у тебя всего один поток в event loop, и это не про GIL, а про то, что нет точки `await`/`yield`, чтобы loop переключился на другую корутину.

### Асинхронный драйвер (`asyncpg`): что происходит под капотом

1. `await conn.fetch("SELECT ...")` вызывается
2. Внутри `asyncpg` сокет переведён в неблокирующий режим (`socket.setblocking(False)`)
3. Драйвер пытается `send()` — если буфер сокета не готов принять данные, вместо блокировки происходит `await` на специальный Future, который зарегистрирован в event loop через `add_writer`/`add_reader` (это используя `selectors`/`epoll`/`kqueue` под капотом — то, на чём построен сам asyncio event loop)
4. Корутина "замораживается" в этой точке, управление возвращается в event loop
5. Loop идёт обслуживать другие готовые к выполнению корутины
6. Когда ОС через `epoll` сигналит "сокет готов на чтение" — event loop возобновляет именно эту корутину с того места, где она остановилась

Грубо: `asyncpg` сам реализует протокол Postgres (бинарный wire protocol) на чистом Python/Cython поверх неблокирующих сокетов, интегрированных с тем же `epoll`, на котором крутится весь твой event loop. Поэтому ожидание ответа от БД — это не блокировка потока, а просто "я зарегистрировал интерес к этому сокету, проснусь, когда будет готово".

> В нашем уроке БД нет — сервисы возвращают статику и ничего не await'ят. Но
> объявлены они `async def` намеренно: когда подключишь реальную БД, тело станет
> `await session.get(...)`, а сигнатуры и весь верхний код менять не придётся.

### Как работать с "внешними штуками" не блокируя loop — общий рецепт

Есть три категории внешних вызовов, и для каждой свой путь:

**1. Есть нативный async-клиент (лучший случай)**

- БД: `asyncpg` (Postgres), `aiomysql`/`asyncmy` (MySQL), `motor` (MongoDB)
- HTTP: `httpx.AsyncClient` или `aiohttp` вместо `requests`
- Redis: `redis.asyncio`

Правило простое: если для твоего "внешнего ресурса" есть async-нативная библиотека — используй её, никаких костылей не нужно.

**2. Нативного async-клиента нет, а синхронная блокирующая библиотека есть**

Тогда уводишь блокирующий вызов в отдельный поток через `run_in_executor`, чтобы он не вис на event loop:

```python
import asyncio

async def call_blocking_lib():
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(
        None,  # дефолтный ThreadPoolExecutor
        blocking_function,  # синхронная функция
        arg1, arg2
    )
    return result
```

Что происходит: `run_in_executor` кидает `blocking_function` в пул потоков, возвращает корутине Future, корутина на этом Future делает `await` — то есть отдаёт управление event loop'у, пока поток где-то в фоне блокируется на синхронном вызове. Когда поток закончит — Future резолвится, корутина продолжается.

Важный нюанс: GIL здесь снова не помеха, потому что пока один поток блокирован в `recv()` (вне Python-байткода, GIL отпущен на время syscall), главный поток с event loop'ом спокойно крутит другие корутины — он-то Python-байткод выполняет, GIL у него свободен.

FastAPI, кстати, делает это автоматически для синхронных `def`-эндпоинтов (через `run_in_threadpool`), но не для блокирующего вызова **внутри** `async def` — там придётся самому. Практический вывод: зовёшь блокирующую библиотеку и не хочешь возиться — объяви эндпоинт обычным `def`, FastAPI сам уведёт его в пул потоков. Объявил `async def` — всё внутри обязано быть неблокирующим.

**3. CPU-bound работа (не I/O, а реальные вычисления)**

Тут `run_in_executor` с потоками не поможет — поток будет занимать CPU и держать GIL во время вычислений (без free-threaded сборки). Нужен `ProcessPoolExecutor` вместо `ThreadPoolExecutor`:

```python
from concurrent.futures import ProcessPoolExecutor

async def cpu_heavy_call():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, heavy_computation, data)
    return result
```

### Резюме-таблица

| Тип ресурса | Решение | Почему loop не блокируется |
|---|---|---|
| БД с async-драйвером | `asyncpg` и т.п. | Неблокирующий сокет + интеграция с epoll |
| БД/HTTP без async-драйвера | `run_in_executor` + поток | Блокировка уходит в отдельный поток, event loop свободен |
| CPU-bound вычисления | `run_in_executor` + процесс | Вычисление уходит в отдельный процесс, не делит GIL с main |

**Итог одной фразой:** event loop даёт конкурентность на одном потоке за счёт
`await` в точках I/O; GIL мешает параллелить CPU-работу потоками. FastAPI быстрый,
пока ты **не блокируешь loop** — для I/O бери async-клиенты, для блокирующего и
CPU-кода уводи работу в пул потоков/процессов.
