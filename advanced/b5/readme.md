# B5. Телеграм-бот на aiogram — планировщик встреч

Пример бота, который хранит встречи пользователя в SQLite и сам напоминает о них
за 1-2 часа до начала.

Урок собирает вместе то, что было раньше: асинхронность из B1, async-ORM из B3 —
и добавляет поверх telegram-бота на **aiogram 3**.

## Что умеет бот

- `/start`, `/help` — справка с HTML-разметкой (`<b>`, `<i>`, `<code>`);
- **создание встречи через машину состояний**: дата -> время -> описание;
- **список встреч** — все будущие встречи пользователя по порядку;
- **нижняя панель** с кнопками «Создать встречу» и «Все встречи» — доступна на любом шаге;
- **напоминания**: раз в час фоновый поток просит бота проверить базу и написать
  тем, у кого встреча начнётся меньше чем через два часа.

## Запуск

```bash
pip install -r requirements.txt
cp .env-example .env        # и вписать туда токен от @BotFather
python main.py
```

Файл базы `meetings.db` создаётся сам при первом запуске рядом с `main.py`.

## Структура

```
b5/
├── main.py                       — точка входа: бот, диспетчер, планировщик
├── requirements.txt
├── .env                          — BOT_TOKEN (в git не попадает)
│
├── config/
│   ├── config.py                 — токен, URL базы, интервалы, метки кнопок
│   └── texts.py                  — все тексты сообщений с HTML-разметкой
│
└── services/
    ├── handlers.py               — регистрация обработчиков (маршрутизация)
    ├── states.py                 — состояния FSM для создания встречи
    ├── decorators.py             — перехват ошибок в резолверах
    ├── utils.py                  — разбор даты/времени, «через 1 ч 45 мин»
    ├── scheduler.py              — поток-расписание + рассылка напоминаний
    ├── db.py                     — Base для моделей
    ├── db_connect.py             — движок, фабрика сессий, создание таблиц
    ├── repository.py             — все запросы к базе
    ├── models/
    │   └── meeting.py            — модель Meeting
    └── resolvers/
        ├── keyboards.py          — клавиатуры нижней панели
        ├── common.py             — /start, /help, необработанные сообщения
        └── meetings.py           — диалог создания встречи и список встреч
```

Логика разложена по слоям: `handlers.py` только решает, **кому** отдать апдейт,
резолверы в `resolvers/` содержат **что** на него ответить, а `repository.py` —
единственное место, которое ходит в базу.

## Используемые модули

| Модуль | Зачем нужен |
|---|---|
| **aiogram 3** | сам фреймворк бота: поллинг, роутер и фильтры, FSM, клавиатуры, HTML-разметка |
| **SQLAlchemy 2.0 (async)** | ORM: модель `Meeting`, сессии, запросы вместо ручного SQL |
| **aiosqlite** | async-драйвер SQLite — база не блокирует event loop бота |
| **python-dotenv** | читает `BOT_TOKEN` из `.env`, чтобы токен не лежал в коде |
| **loguru** | логи запуска, проверок планировщика и ошибок |
| **asyncio** (stdlib) | event loop, в котором живут и поллинг, и напоминания |
| **threading** (stdlib) | поток-расписание, который раз в час будит проверку |
| **html.escape** (stdlib) | экранирует текст пользователя, чтобы `<` не ломал HTML-разметку |

## Два места, ради которых написан пример

### Машина состояний (FSM)

Встречу нельзя создать одним сообщением — бот спрашивает данные по шагам. За то,
«на каком шаге сейчас пользователь», отвечает состояние (`services/states.py`).
Пока состояние установлено, текст пользователя попадает в обработчик именно этого
шага; промежуточные ответы копятся в хранилище FSM (`state.update_data`) и
превращаются в строку базы только на последнем шаге.

Отсюда — важность **порядка регистрации** обработчиков в `handlers.py`: кнопки
нижней панели зарегистрированы до состояний, иначе нажатие «Все встречи» на шаге
ввода описания сохранилось бы как текст встречи.

### Поток, который кидает задачу в event loop бота

`services/scheduler.py` — отдельный `threading.Thread`. Он **не** работает с базой
и не отправляет сообщения сам: он только спит на `threading.Event.wait()` и раз в
час передаёт корутину в event loop бота через

```python
asyncio.run_coroutine_threadsafe(send_reminders(bot), loop)
```

Это единственный безопасный способ достучаться до event loop из другого потока —
объекты asyncio не потокобезопасны. Возвращается обычный
`concurrent.futures.Future`, чей `result()` блокирует поток планировщика, но не
цикл событий. В итоге бот и напоминания живут в одном event loop и делят одно
подключение к базе, а расписанием заведует поток снаружи.

Окно напоминания (2 часа) намеренно больше интервала опроса (1 час) — так ни одна
встреча не проскочит между проверками. Чтобы одна и та же встреча не попала в две
соседние проверки, у модели есть флаг `reminded`.
